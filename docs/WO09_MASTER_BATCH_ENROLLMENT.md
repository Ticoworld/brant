# Native signed batch enrollment

VERIFIED actual native funding and signature execution, not OTX. One shared vault transition applies sequential authenticated leaf updates, with each contributor supplying its own funded plain secp input and receiving its own change. Every empty index is unique within a batch; each old empty leaf is proven against the current intermediate root. Each new right receives exactly floor(4p/5) backing. The aggregate contribution, backing and claim counters and actual vault capacity must agree. Duplicate indices, oversized envelopes and forged paths are checked independently of wallet signatures.

The bounded client uses one contributor per wallet signature group and exactly one change output per contributor. All except the final contributor lose precisely their declared contribution; the final contributor additionally pays the explicitly signed miner fee. This is a declared fee-allocation policy, not a free aggregator. A missing contributor signature rejects at the actual secp lock. A duplicated input rejects at native resolution as Dead; the test checks the actual Cell remains live before and after and the outpoints are identical. That is a resolver result, not a type-script security PASS.

Complete native markets at 16,100,1,000 owners are in merkle-scale-1793668842445. One batch of 16 funds the 16-person market; one batch of 100 funds the 100-person market; ten batches of 100 fund the 1,000-person market. Every market activates, partially redeems, assigns a purchased right, redeems all remaining owners and closes with zero outstanding backing. The same code publication and previously funded participant Cells are reused across the three markets.

Actual batch sizes/cycles: 16 at depth 4: 8,232 bytes / 31,173,545 cycles / 17 inputs / 17 outputs. 100 at depth 7: 58,000 bytes / 315,532,688 cycles / 101 inputs / 101 outputs. 100 at depth 10: 67,600 bytes / about 360.7 million cycles / 101 inputs / 101 outputs. Each tested large batch pays 100,000 shannons. The 101-update attempt rejects due to the explicit contract envelope cap; this is not a universal CKB maximum.

## Failures and corrections

Standard system secp v0.5.4 defines error -22 as ERROR_WITNESS_SIZE and each witness maximum as 32,768 bytes. The original single extra witness for 100 depth-7 updates was 32,816 bytes and failed in the actual secp script. Official source is pinned to e08e6016f16072fc2f44cf889ae063fa5b7e10c7; its Cargo manifest declares MIT and original authors. Research source/provenance is preserved. The protocol correction splits the complete payload into at most four additional witnesses, with the client choosing 16 KiB chunks. Canonical sighash signs every extra witness and its length; the covenant concatenates them, enforces a total maximum, and requires an exact count/depth-derived payload length. It does not skip signatures, omit records or ignore trailing data. The new binary is 17,488 bytes, SHA-256 925f4c387f34d8c0f2129dfa9cd3587ce6601158b18cdf5d1bbf2684cd2f5a7a. The one-witness v1 remains frozen.

A presumed hard rejection above the configured 70 million cycle value was falsified by actual admission and subsequent commitment. No node configuration was changed. Official CKB v0.210.0 process code shows transactions above the configured value routed to a verification queue. Definitive committed results, not the initial RPC hash alone, establish the result. The large-batch runner allows asynchronous verification time before asserting commitment. Research requests use the existing experimental outputs-validator option; consensus and script checks remain enabled. Public deployment/relay behavior is not claimed.

A separate early run completed 16 owners but then reused the consumed funder input at the next market. Correcting the wallet successor fixes the builder without changing the covenant. All failing traces remain preserved separately.

## Stronger rival: smaller batches

At the same 100-owner target, an additional complete native lifecycle uses seven batches of up to 16: 61,488 total enrollment bytes and 208,662,624 cycles, versus one 100-owner batch's 58,000 bytes and 315,532,688 cycles. Smaller batches use about 6% more bytes and about 34% fewer cycles, but require seven shared-state transitions and more signing rounds. Selected fees were 70,000 total versus 100,000 shannons; these are client choices, not an intrinsic fee saving. At equal 1 shannon/byte, smaller batches instead require slightly more fee. Every signature hashes a large complete transaction, so batching has more than just logarithmic Merkle costs.

All parties sign an assembled whole transaction bound to one current root. They do not provide independent reusable funding intents. A coordinator can refuse to assemble, and concurrent vault activity can require new assembly/signatures. Anyone can build a permitted batch; inclusion and willing coordination are not guaranteed. CoBuild/OTX or pre-funded pledge Cells are separate alternatives requiring their actual authorization/storage trade-offs, not renamed versions of this batch protocol.

## Configured-policy requalification

The isolated configured covenant repeats real native 16/100/1,000-owner execution (`merkle-configured-scale-1793671317288`). First batch at 16: 8,256 bytes / 31,198,255 cycles; at 100: 58,024 / 315,167,022; at 1,000 (100 enrolled at once): 67,624 / 360,655,109. The latter has 101 inputs/outputs, 100 actual independent owner signature groups, and 42,416 transition bytes split across signed witnesses. Code/vault policy overhead is included in these complete measurements. A missing contributor signature rejects in the standard lock. Duplicate input tests verify an actually live source Cell and native resolver rejection; they are not covenant errors. Raw transaction signatures and every funded outpoint are preserved.

Every contributor signs the complete current transaction, including the latest shared vault input, all change outputs, fees and framed proof bytes. Builders may coordinate contributions in parallel before final signing, but these are not independent reusable funding offers. Root changes invalidate that assembled transaction; contributors must sign a rebuilt one. There is no implemented OTX signed-intent/range protocol or guaranteed inclusion. An aggregator can assemble a batch permissionlessly but must obtain signatures, can refuse service, and has no proven real incentive/bid. All but the final contributor pay exactly their recorded contribution; the last pays the explicitly signed miner fee as well. Alternative fee sharing is not implemented. Every update path applies sequentially within the batch; the last root authenticates precisely those funded records.

Same-target smaller-batch comparison remains native evidence for the frozen framed version: seven <=16-person batches total about 209M cycles and 61,488 bytes versus one 100-person batch about 315.5M and 58,000 bytes. This reflects transaction/signature overhead and shared-transition trade-offs, not a measured 16-person optimum for all configured workloads. Maximum supported update count is 100, including at target 1,000; native 101-update rejection is preserved. Distinct markets/cohorts can use independent vaults; one global vault retains serialization and no anti-starvation guarantee.
