## B1. Mathematical solvency

Start from exact accounting.

For one illustrative bilateral contract:

`ProtectedPayout = min(AvailableCollateral, USDTarget / ValidSettlementPrice)`

`ResidualPayout = AvailableCollateral - ProtectedPayout`

This is one possible bounded payoff, not a mandatory architecture.

Use exact integer/rational arithmetic.

Test CKB price movements of:

- Down 20%.
- Down 50%.
- Down 80%.
- Down 99%.
- Unchanged.
- Up 25%.
- Up 100%.
- Other boundary conditions.

Determine:

- What is actually protected?
- Which party absorbs losses?
- What happens when collateral is exhausted?
- What premium is required?
- Can the junior side lose all collateral?
- Is the claimed leveraged exposure accurately measured?
- What is the capital efficiency?
- How much is locked until maturity?
- Does the product outperform simply holding or selling CKB?
- Who would rationally take each side?

### IF / ELSE questions

# 8. MANDATORY IF / ELSE / WHAT IF INVESTIGATION ENGINE

Use this cycle throughout:

**OBSERVE → QUESTION → HYPOTHESIS → FORMALIZE → IMPLEMENT → ATTACK → DEBUG → REDESIGN → REPRODUCE → COMPARE → DECIDE**

Maintain a chronological research journal recording why each decision was made.

## IF an experiment fails due to implementation

Determine whether the problem is:

- Wrong script.
- Bad witness.
- Incorrect signature.
- Wrong dependency.
- Inaccurate capacity.
- Incorrect DAO epoch.
- Missing state.
- Invalid fee assumption.
- Broken transaction builder.
- Compiler/runtime mismatch.
- Actual consensus rejection.
- Test harness defect.

Reproduce the failure.

Correct the defect.

Add a regression test.

Run the experiment again.

Do not call a mechanism impossible because the implementation was faulty.

## ELSE IF a design fails mathematically

Construct the minimal counterexample.

Identify the violated assumption.

Investigate materially different architectures.

Do not merely change constants or remove failing tests.

Examples:

- Global reserve versus independent claims.
- Fixed floor versus pro-rata entitlement.
- Pooled versus individually funded collateral.
- Constant prices versus authorized price commitments.
- Auction versus matching.
- Single maker versus competing makers.
- Permanent versus time-bounded obligations.
- Native CKB versus other fully accounted collateral.
- Unified versus modular contracts.

Stress-test whether the correction introduces a worse failure.

## ELSE IF a mechanism fails economically

Identify why.

Is it due to:

- Too much locked capital?
- Unfunded compensation?
- Uncompetitive fees?
- No natural counterparty?
- No genuine customer demand?
- Inventory depletion?
- Adverse selection?
- Oracle operating costs?
- Insufficient creator financing?
- Weak secondary liquidity?
- Better existing competitors?

Investigate whether changing the economic design meaningfully solves the problem.

Do not assume a technically valid architecture has a viable business.

## ELSE IF a known competitor already solves the same problem

Inspect the strongest competitor's implementation.

Try to establish a meaningful improvement:

- Stronger independent ownership.
- Better recovery.
- Better execution rights.
- Less occupied capital.
- Lower complete lifecycle cost.
- More useful issuance.
- Safer settlement.
- Better price formation.
- Stronger creator economics.
- Reduced trusted dependencies.
- Better access to existing liquidity.

If no advantage survives, reuse the existing solution or redirect attention to a stronger market opportunity.

Do not claim novelty by renaming existing features.

## ELSE IF a design passes

Freeze it as a working fallback.

Do not immediately polish or package it as a product.

Attack the highest-ceiling unresolved assumption.

Compare against stronger alternatives.

Test larger, more adversarial or economically meaningful conditions.

## ELSE IF a stronger design emerges

Change direction.

Preserve the earlier evidence.

Build the smallest decisive proof for the new hypothesis.

## ELSE IF two designs complement each other

Test the combination.

Recalculate all claims and collateral.

Measure added complexity and new failure states.

Only promote the combined design if it produces meaningful additional value.

## ELSE IF a specific approach is exhausted

Record the actual boundary.

Preserve the useful research.

Continue independent promising directions.

Do not keep generating superficial variants of the same disproven assumption.

Do not stop all Trade research because one contract or product hypothesis fails.
