## Transaction and funding

An exact executable unsigned Pudge assignment cannot yet be constructed: a verified R7 code deployment, live R7 vault and live seller/recipient input outpoints do not exist in the verified preflight. Do not substitute the prior private outpoints. The exact op4 shape is documented by `apps/trade-testnet/tests/r7-extension-prepare.cjs`: inputs 0 vault, 1 current owner standard lock, 2 recipient standard lock; outputs 0 successor vault with preserved principal/backing and incremented revision, 1 seller wallet with positive consideration, 2 recipient change wallet; witness 3 carries the op4 leaf updates and current Merkle proof. Seller and recipient standard-lock groups each sign the same final transaction; the covenant verifies the vault group. The supplied recipient address resolves to standard-lock hash `0xc47b33f79bb3439876bf5be3af7d790eca8ae73779346297b5290ad73e4436ca`. Both wallet outputs must satisfy occupied capacity and the transaction fee must not exceed the covenant's 1,000,000-shannon ceiling. Final bytes, outpoints, fees and human-readable exact transaction require live cells and cannot be honestly precomputed now.

For illustration only, a single-position scenario with 1.25 CKB principal, 1 CKB backing and an 80 CKB assignment, assumes code 51,113 CKB, vault cushion 354 CKB, deployer/funder and seller plain cells each 61 CKB, and recipient input at least 141 CKB plus fee to leave 61 CKB change. A rough simultaneous capacity envelope is 51,113 + 354 + 61 + 61 + 141 + 1.25 = 51,731.25 CKB plus fees, contingent on ownership and funding schedule; it is not a verified exact balance requirement. Transfer consideration moves between participants, backing remains locked, code and cushions are capital rather than network fees. Creation, activation, assignment, unrelated update, sale, potential consolidation and deployment fees are additional and require actual transaction sizes and Pudge fee-rate checks. Actual capacity can be higher with distinct actors, minimum output constraints and funding change. Code-cell recoverability depends on its chosen lock.

## Wallet and blockers

Installed CCC 1.23.0 UTXO Global adapter selects `nervos_testnet` for a non-mainnet client and passes transaction signing to `provider.signTransaction`; installed extension code fetches each input's previous output using its configured CKB RPC. The failed private attempt could not resolve its private vault input. Pudge input lookup is plausible but actual Pudge transaction signing and provider endpoint have not been observed. Real UTXO Global message signing was verified in R7E's isolated VM, not a funded R7 sale.

The current R7 UI/service deliberately requires loopback `ckb_dev`; it cannot perform the Pudge R7 journey as-is. Live discovery, verified deployment configuration, public transaction review, fee calculation, stale/unknown recovery, backend idempotency, reorg handling, security review and archival-history availability remain gates. No complete real-wallet trial is technically ready. Existing R7 tests are private-chain evidence, not a public-chain security audit or throughput claim.

Before any Pudge action, prepare and independently review a concrete deployment transaction and funding plan, specify deployment lock and owners, verify live cells/genesis/dependencies and current fee rate, and obtain explicit approval for deployment and spending. After deployment, construct and review the exact creation, funding, activation and assignment transactions, with each relevant wallet signature and public broadcast individually authorized. A later seller message signature binds live terms; the buyer separately signs a fill. Do not assume prior message authorization applies to the new Pudge vault.
