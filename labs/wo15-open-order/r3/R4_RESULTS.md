# WO15 R4 focused native qualification

Status **B — native correctness gate remains open**. All transactions below used a disposable private CKB 0.210.0 chain and fixture keys. No public deployment or spend. The R3 contract was not changed. The parent `run-r4-identities.cjs` recreates the experiment; `node labs/wo15-open-order/verify-r4.cjs labs/wo15-open-order/evidence/r4-identities-1793907669629` independently checks recorded transaction fields and committed node responses, not consensus independently.

## Identity and settlement

**COMMITTED:** two separately funded orders used distinct code data hashes `9d9284...f848` and `814bdc...1955`, both `data1`, distinct maker locks, and distinct xUDT type hashes. The second binary is the identical original ELF followed by one zero byte: its different data hash is a separate code identity, not an independent implementation. Both were loaded from different genesis code cells and executed in one settlement. Buyer input was index 0; order inputs were 1 and 2; two unrelated buyer outputs preceded each order's indexed payout/delivery pair. Committed settlement: `0x95a7361fddad768871f129fc73872399beb7a0c6e5a274b63d3c43dcd9c1d01b`. The node reported maker outputs 310 and 410 CKB (210 returned plus 100 and 200 consideration), and two live 142 CKB buyer Cells each holding 1,000 of the respective token. Both consumed order outpoints were reported `unknown` by `get_live_cell`. Offline trace verification confirms the input/output relationships and node-reported committed status.

**CORRECTLY REJECTED:** the second maker's underpayment and a misplaced second payout both failed at input 2's order lock with error 26. This is focused evidence, not proof of every output ordering. Same-asset aggregation remains prohibited. Distinct-maker inputs in a batch can invoke their cancellation branch; this fixture deliberately has only the buyer's standard-lock input, so both order locks execute fill checks.

**VM INCOMPATIBLE:** the previous R3 `data` attempt failed `MemWriteOnExecutablePage`; `data1` for this ELF works. RFC 32 maps `data` to v0 and `data1` to v1. RFC 33 documents v0 executable-page and frozen-page bugs; the failure is consistent with VM-v0 compatibility, but the exact failing instruction/loader path was not isolated. The test qualification supports `data1` only. Do not fund this binary with `data`.

## Cancellation, lineage and limits

**COMMITTED:** a separately signed cancellation returned its order's 1,000 xUDT and 210 CKB to the maker. It committed before a previously prepared fill, whose later estimate failed unresolved outpoint. Conversely, a cancellation prepared before the two-order fill failed unresolved outpoint after that fill committed. These are sequential confirmed schedules, not a simultaneous mempool competition or evidence of transaction priority. A maker-authorized cancellation also returned a plain 210 CKB Cell with malformed data and no type. Malformed script length remains unrecoverable through this binary because script parsing precedes authorization. Cancellation itself checks a maker-lock input, not destination: the maker signs and must review the complete transaction to ensure recovery; a third-party builder must not be trusted.

The fixture derives listings from committed funding transactions, resolved maker-lock inputs and live order Cells, then records chain genesis, binary and asset identities, terms and status in `listings.json`. This is **fixture-specific**, relying on the private node, known standard secp lock semantics, and the maker's full-transaction signature. It is not a general arbitrary-lock authorization verifier, independent consensus proof, durable discovery service, or proof that an issuer's xUDT is economically genuine. A listing status is a snapshot; both listed orders were subsequently consumed. Relay metadata alone is not authentication. Real UTXO Global funding/fill/cancellation prompts and signing compatibility remain untested.

## Capacity and economics

**COMMITTED:** this exact order shape uses 210 CKB occupied capacity and buyer xUDT outputs use 142 CKB each. The 300 CKB R2 value was conservative. **CORRECTLY REJECTED:** an otherwise funded 209 CKB order failed `send_transaction` with `InsufficientCellCapacity(Outputs[0])`; crucially, `estimate_cycles` had accepted the same candidate, recorded in partial run `r4-identities-1793907652040`. For this exact shape, 210 is the calculated and tested occupancy floor, not a fee.

The two-order fill serialized to 1,526 bytes and estimated 1,725,576 cycles; the fixed fee was 0.01 CKB. Each separate order funding was 718 bytes and cost a fixed 0.01 CKB; cancellation was 687 bytes and 0.01 CKB. Exact cycles are in the events, and transaction fees are fixture values, not market estimates. Buyer receiving-cell capacity is independently funded and recoverable subject to future spending; maker order capacity is returned on the shown fill and cancellation. For 100 and 200 CKB consideration, the 210 CKB locked maker capacity is respectively 210% and 105% of order price, before inventory and fees. It is not a permanent fee. Time locked, market impact, order sizes beyond these, capital opportunity cost and actual deployment fees have not been measured. The 4,240-byte binary requires approximately 4,301 CKB in a no-type code Cell using a 20-byte-args ordinary lock; this is a derived occupied-capacity estimate, not a measured deployment. Genesis insertion paid no deployment transaction fee.

Existing A2 two-order shared settlement: 1,156 bytes, 1,779,901 estimated cycles, 0.01 CKB fixture fee, funding excluded (`docs/REBUILD_NATIVE_EXECUTION_EVIDENCE.md`). Its rights, cell layout, token direction and workload differ, so these numbers do not rank net execution or safety. An OTX implementation was not benchmarked here; no capital-efficiency or wallet-compatibility conclusion is claimed.

## Still open

Test more absolute input positions and missing outputs, independent buyers and concurrent pool submissions, adverse signing/witness variants, arbitrary supported lock funding lineage and reorg handling, authenticated durable discovery, deployment and full lifecycle economics, and real CCC/UTXO Global wallet behavior. No hard upper expiry is enforced. Without those checks and independent review the execution-service gate stays closed. Passing these private fixtures does not make the contract audited or production secure.
