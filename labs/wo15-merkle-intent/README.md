# WO15-R5: experimental offline intents for the financial Merkle vault

**B — core demonstrated; wallet, concurrency and security gates remain.** This is a private-chain experiment, not an audited contract, deployed product, xUDT exchange, or CoBuild OTX implementation. The configured source and deployed Pudge binary are untouched. `contracts/merkle_intent.c` is an isolated derivative of `labs/wo09-unified/contracts/merkle_market.c` with the configured policy enabled.

The committed binary is 61,032 bytes; CKB data hash `0x04a97d1560b2ad7704d456229cf3837383ac7eb65a9b94be5a500470770045e8`; SHA-256 `a27ead2bdd39b8180cfc138cc5847af2a583ff2bdcb49dae0f3a954be351a084`. ## Intent and immutable policy

This proprietary authorization signs a CKB-personalized Blake2b-256 digest of exactly: 16-byte ASCII `TRADE-WO15-R5-v1`, genesis hash32, vault ID32, covenant full script hash32, position index u64 LE, old leaf56 and minimum price u64 LE. The leaf is owner script hash32, principal u64, backing u64 and revision u64. The Zig standard-library secp256k1 adapter verifies a 64-byte compact ECDSA signature using SHA-256 of that digest. The contract derives a CKB standard secp lock hash from the supplied compressed public key and compares the *full lock hash* to the authenticated current leaf owner. Host fixture signatures use elliptic; a separate replay also verifies them with elliptic. Neither is proof of UTXO Global compatibility.

Every changed leaf increments its revision. Empty slots retain their revision as an authenticated tombstone, preventing reuse of a prior signature after transfer away and back or supported re-enrollment. An intent names the old leaf but not the global root or future buyer outpoint, so a fresh proof against a different root can be used while that leaf stays unchanged. On-chain owner-authorized op9 increments the revision to revoke outstanding intents; off-chain cancellation is advisory. Cancellation races remain subject to transaction ordering. There is no hard upper expiry. Genesis is bound via a committed genesis header dependency; this does not distinguish forks sharing genesis.

Op8 uses exactly a vault input plus one buyer funding input. All purchased leaves are assigned to that buyer, preserve principal and backing, and have distinct leaf indices. Seller j has a separate plain standard-lock payout output j+1 at least equal to their signed minimum. The buyer funds payouts and network fee, bounded by the inherited 1,000,000-shannon transaction fee limit. Each new payout Cell must also meet occupied capacity (61 CKB for the fixture's standard lock). The existing configured market's financial covenant, policy fields, conservation checks, closure conditions and funding restrictions are retained in the isolated derivative; they have not been exhaustively requalified after the leaf-format changes. This scheme does not claim a rising redemption floor or create a token.

## Capacity, cost and competing mechanisms

The code deployment really committed and occupied 61,073 CKB (61,032-byte code plus 41-byte code Cell overhead in this fixture), with 0.01 CKB fixture fee. Its output uses an unspendable lock in this setup, so do not assume recovery. A shared vault uses a 354 CKB cushion plus actual backing liabilities. Seller payout Cells require real capacity, buyer funding and future spendability; code, vault cushion, wallet capital and liquidity are not zero. The configured predecessor used 17,889 CKB code and 322 CKB cushion. This candidate's larger cryptographic code and roughly 27 million additional cycles per signature are substantial costs.

R4 two distinct-asset orders settled in 1,526 bytes / 1,725,576 estimated cycles with 210 CKB occupied per order and 142 CKB per buyer token Cell; R4 is a different xUDT service. If comparing only cold code and shared state versus R4's estimated 4,301 CKB code and 210 CKB/order, the algebraic state-capital crossover is 273 simultaneous orders: `61,073 + 354 <= 4,301 + 210*N`. This omits financial backing, payout Cells, token receiving Cells, user wallets, existing deployments, liquidity and differing rights, and is not an economically demonstrated break-even. Actual order prices, fees, duration, revocation and sellable claims differ.

Existing A2 two-order shared clearing measured 1,156 bytes / 1,779,901 estimated cycles with a 0.01 CKB fixture fee, funding excluded. Historical 1,536-order optimized A2 is a distinct, genuinely executed workload, not a capacity claim for this contract. No like-for-like CoBuild OTX benchmark was executed; no numerical superiority is claimed. This fusion permits root-independent maker authorization but creates serial shared-state contention and high secp verification costs.

## Product and compatibility gates

These are financial claim records, not externally transferable xUDT. A floor-backed token would separately need a defined issuer and supply, per-unit backing and conserved redemption liabilities, burn/payout and rounding rules, partial redemption, insolvency constraints, and protection against using both an external token and an internal claim to redeem twice. No token or launch product is implemented. The previous cash-only 80/20 offer remains commercially unproven.

Installed CCC's UTXO Global adapter exposes message signing but delegates it to the wallet provider. CCC's documented CKB message scheme uses a `Nervos Message:` domain and recoverable signature; the present SHA256-over-intent-digest compact format differs. We have not observed the provider's actual signature, approval screen or handling of economic terms. No real wallet signature was made. A usable wallet-compatible signing format, its full on-chain validation, human-readable authorization, independent security review, recovery/reorg and data-availability tests, distinct-buyer batching, cancellation/solver race study and comparable executable economics remain before any application integration or public deployment. No live liquidity, independent audit or trading-speed superiority is claimed.
